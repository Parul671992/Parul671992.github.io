Agentic Upskilling Planner

An AI agent that builds week-by-week upskilling plans, checks its own work before anyone sees it, and lets a person approve or push back.

Watch the 2-minute demo Read the code on GitHub

Built by Parul. Python, LangGraph, RAG, MCP, Docker.

6DeliveredBy email or in your AI assistant

Why I built it

Most AI demos stop at "the model gave an answer." I wanted to work on the harder part: how do you know the answer is any good, and what happens when it isn't?

A learning plan was a good test for that. It has hard rules a computer can check (does it fit in 4 weeks? does every resource actually exist?) and softer ones that need judgment (is this too advanced for a beginner?). So the agent drafts a plan, a second AI reviews it, and if the plan doesn't hold up, it goes back for another round. A person can step in at the end and overrule both.

I spent more time testing, breaking and fixing this than building the first version, and that's the part I'm proudest of.

The short version for recruiters: a multi-step AI agent with a self-correction loop, retrieval over your own documents, a human approval step, an automated evaluation suite, and a tool API that other AI apps can call. It runs in Docker.

How it works

Six steps, two loops. If the reviewer isn't satisfied, the plan gets reworked, up to three rounds. If a person asks for changes, their instructions win.

See it run

A form submission goes in, the agent researches and reviews, and a formatted plan lands in the inbox. Then the same agent, called from Claude Desktop, pauses for my approval.

Architecture decisions

The choices that shaped the system, what I picked instead, and what each one cost me.

LangGraph for the main version, not CrewAI

Why
The critique loop is a cycle, and LangGraph supports cycles and saved state natively.
Instead of
CrewAI, which I built in full to compare. Its sequential mode needed a hand-written outer loop, and hierarchical mode hit a known bug.
Cost
More code to write by hand than CrewAI's role-based setup.

Code decides when to stop, not the model

Why
An LLM reviewer can keep finding small issues forever. A hard cap of 3 rounds in the routing code guarantees the run ends.
Instead of
Trusting the reviewer to say "good enough" on its own.
Cost
A plan can hit the cap without approval, so it gets a note asking for a manual look.

One shape for web and document results

Why
Web search and retrieval from your own files both return the same SearchResult structure, so the planner never knows which one ran.
Result
Adding RAG mode needed zero changes to planning, writing or review.
Cost
Document chunks have to fit fields designed for web pages, so the file path stands in for a URL and the page number goes in the title.

The human outranks the AI reviewer

Why
Human feedback lives in its own field that is never overwritten, and both the planner and the reviewer must follow it.
Instead of
Sharing one feedback field, which let the AI reviewer erase the person's instructions.
Cost
Prompts get longer as feedback piles up across rounds.

Saved state in a file, so a review can wait

Why
The graph pauses for a person and saves its full state to a SQLite file. A completely new process can pick it up later with just an ID.
Instead of
In-memory state, which disappears the moment the program stops.
Cost
Loading saved objects is a security risk, so only two known classes are allowed back in.

Two tools for review, not one

Why
An MCP tool call is a single request and response, so it can't sit and wait for a human. One tool starts the review, another resumes it.
Result
Any MCP client, like Claude Desktop or n8n, can run the full human-approval flow.
Cost
The caller has to keep track of the review ID between calls.

What broke, and how I fixed it

The bugs taught me more than the build did.

The reviewer never said yes

Symptom: every single run hit the 3-round cap.

Cause: my prompt said "be critical, not lenient" but never defined good enough.

Fix: explicit approval criteria. Runs now finish in 1 to 2 rounds. Lesson: vague instructions give an LLM inconsistent behavior.

A book that didn't exist

Symptom: on its first runs, my eval suite flagged a plan recommending a book that search never returned.

Cause: the prompt forbade inventing resources, but nothing checked.

Fix: an automatic grounding check on every resource and every link, with unit tests that feed it fake plans to prove it catches them.

The AI overruled the human

Symptom: I rejected a plan with "use only YouTube videos," and the reviewer kept rejecting the compliant plans.

Cause: the reviewer never saw my feedback, and its own notes overwrote mine.

Fix: a separate human feedback field that outranks the reviewer.

A loop that silently stopped looping

Symptom: in the CrewAI version, the reviewer rejected the same write-up three rounds in a row. It looked like the reviewer was too harsh.

Cause: the writer task was returning cached output, word for word, even though the plan had changed. I caught it because the write-up still named a course that no longer existed anywhere in the plan.

Fix: turned off caching on every task. One of 5 framework bugs I documented in the comparison write-up.

Random timeouts in Claude Desktop

Symptom: the MCP server sometimes failed to connect, with no code change.

Cause: the embeddings library quietly checked the internet on every start.

Fix: offline mode, and in Docker the model is downloaded once at build time.
