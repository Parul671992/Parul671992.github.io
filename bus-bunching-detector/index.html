Real-Time Bus Bunching Detector

You wait 20 minutes for the bus, then two arrive together. This system watches live Boston bus data and flags the moment buses on the same route bunch up.

Read the code on GitHub See the design decisions

Built by Parul Jindal. Java 21, Spring Boot, Apache Kafka, Docker.

1PollLive MBTA bus positions, every 10 seconds
2PublishTo Kafka, keyed by route
3PartitionEach route in order, kept 24 hours
4DetectSame route and direction, within 300 m
5AlertOnce per pair, bad data set aside
6On the mapLive buses and the routes that bunch most

Why I built it

I ride MBTA buses and see this almost every day: a long wait, then two buses arrive together, one packed and one nearly empty. It's called bus bunching. One bus falls a little behind, picks up extra riders at every stop and slows down even more, while the bus behind it catches up.

The MBTA publishes the live GPS position of every bus for free. So the question became: can I spot bunching the moment it starts, and keep a record of which routes bunch the most? A dispatcher who knows early can hold the trailing bus for a minute and even out the gap.

I also used it to learn Kafka properly, not just call it. I built each guarantee, then broke it on purpose: I stopped services mid-stream, scaled past the number of partitions and fed it garbage, to see what Kafka actually does.

The short version for recruiters: three Spring Boot microservices connected by Apache Kafka, running on live MBTA data. Route-keyed partitions for ordered, stateful detection without a database, two consumer groups reading one topic, retries with a dead letter topic, at-least-once delivery, event-time replay, and Testcontainers integration tests in GitHub Actions. It runs with one Docker Compose command.

How it works

Every bus position takes the same path. Kafka keeps each route's positions together and in order, so the detector can compare buses without a database.

Architecture decisions

The choices that shaped the system, what I picked instead, and what each one cost me.

Key messages by route, not by bus

Why
Kafka keeps order only inside a partition, and the key picks the partition. Keying by route sends every route 39 position to one partition and one detector, so it sees all route 39 buses, in order, and can compare them in memory.
Instead of
Keying by vehicle, which would scatter a route's buses across detectors so none of them could spot two buses close together.
Cost
A busy route makes its partition busier than the others, and one route can never be split across detectors.

Event time, not the server clock

Why
Staleness and alert cooldowns use each position's own MBTA timestamp. Rewinding to replay a day gives the same alerts it would have given live.
Instead of
The server clock, which would make every replayed position look hours old, so nothing would ever be detected.
Cost
The system trusts the MBTA's timestamps to be right.

A dead letter topic for bad data

Why
One message that always fails would otherwise be retried forever and block every message behind it. Unreadable JSON and impossible coordinates go straight to a dead letter topic, with the error in the headers.
Result
Unexpected errors still get two retries, one second apart, because those can be temporary.
Cost
An extra topic that someone has to check.

Commit only after the alert is stored

Why
The detector waits for Kafka to confirm each alert before its position counts as read. A crash in between means the position is read again, never skipped.
Instead of
Sending alerts without waiting, which is faster but can silently lose one.
Cost
At-least-once delivery: a crash at the wrong moment can repeat an alert.

Two consumer groups on one topic

Why
The detector and the live map both read every position, each in its own consumer group with its own offsets. A slow or stopped detector never affects the map.
Instead of
Having the detector pass positions along to the map, which would tie the two services together.
Cost
Each group reads the full stream.

State in memory, rebuilt from Kafka

Why
The detector only needs each bus's latest position from the last 2 minutes, so a plain map in memory is enough. Kafka is the source of truth.
Instead of
A database, or Kafka Streams state stores, which add moving parts this scale doesn't need yet.
Cost
After a restart, detection needs about 2 minutes of new positions to warm up.

What broke, and what I learned

I broke the system on purpose to see how Kafka handles failure. One bug I didn't plan for showed up in CI.

I fed the detector garbage

Test: I sent the plain text "hello" to the positions topic from Kafka UI.

Result: it landed on the dead letter topic with the exception in its headers, and the detector kept processing real positions.

Why it works: an error-handling deserializer turns the crash into an error the handler can route, and unreadable data is never retried.

I stopped the detector mid-stream

Test: I stopped the detector while the ingestion service kept publishing.

Result: its lag grew in Kafka UI. When I restarted it, it resumed from its saved offsets and caught up to zero.

Lesson: Kafka is a buffer, not just a pipe. Nothing waits on the consumer, and nothing is lost when it's down.

I scaled to 4 detectors, and 9 consumers sat idle

Test: I ran 4 detector containers.

Result: 12 consumers joined the group (4 containers, 3 threads each), but only 3 got a partition. The other 9 waited as standbys.

Lesson: partitions cap parallelism. Each container already runs 3 threads, so one container uses all 3 partitions. More readers need more partitions.

The dead letter test failed in CI

Symptom: in GitHub Actions, 9 of 10 tests passed. The integration test expected 2 messages on the dead letter topic and found none.

Cause: I built the dead letter producer from the address in the config file. Docker Compose overrides that address, so it worked on my laptop, but the test's Kafka ran on a random port.

Fix: build it from the producer Spring had already connected. Lesson: a test against a real broker caught a bug manual testing never would.
