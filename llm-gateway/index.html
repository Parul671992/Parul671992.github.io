Multi-Tenant LLM Gateway

A gateway that sits between apps and LLM providers, so each customer's AI usage stays fast, affordable and within budget, even when a provider goes down.

Read the code on GitHub See the design decisions

Built by Parul Jindal. Java 21, Spring Boot, Redis, PostgreSQL, Docker.

1RequestAn app sends a question with its API key
2Key checkHashed key, Redis first, then PostgreSQL
3Rate limitEach customer's requests per minute
4CacheSame question? Answered in milliseconds
5BudgetStopped before a customer overspends
6AnsweredBy Groq, or Gemini if Groq is down

Why I built it

Every startup adding an AI feature hits the same wall. Each LLM call costs money, even when a hundred users ask the same question. Answers take seconds. The provider rate limits your whole account, so one busy customer can block everyone else. And when the provider has an outage, your feature goes down with it.

A gateway in the middle can fix all of that, but only if it is built carefully. A cache that serves stale data, a rate limiter that breaks when Redis does, or a failover that hides real bugs can do more harm than good.

So I built it the way I would want it built in production: I broke every feature on purpose, measured what happened, and fixed it before trusting it. Along the way, every caching pattern that comes up in backend interviews became a real feature: cache-aside, write-through, TTLs, eviction, stampedes and drift.

The short version for recruiters: a multi-tenant Spring Boot service with hashed API keys, per-tenant rate limits and budgets, a Redis cache with distributed-lock stampede protection, automatic LLM failover behind a circuit breaker, metrics, and 22 automated tests including Testcontainers integration tests. It runs as a production-style Docker image.

How it works

Six checks, cheapest answer first. A repeated question is answered from the cache without touching the LLM, and a request that fails a check is stopped before it costs anything.

Architecture decisions

The choices that shaped the system, what I picked instead, and what each one cost me.

Cache-aside for answers, write-through for budgets

Why
Answers are many and read unevenly, so they fill lazily on a miss. Budgets are read on every request and must be right the moment an admin changes them, so every write updates PostgreSQL and Redis together.
Instead of
One caching pattern for everything.
Cost
Two code paths to reason about, and every budget update does two writes.

A Redis lock for stampedes, not a Java lock

Why
SET NX with a TTL lets one request rebuild an answer while the others wait, across every running copy of the app. A Lua script releases the lock only if the caller still owns it, in one atomic step.
Instead of
A lock inside the JVM, which stops working the moment Kubernetes runs a second pod.
Cost
Waiters add about 50 ms of polling, and need a timeout and a fallback so nobody waits forever.

Fail open for the cache, never for security

Why
If Redis is down, answers come straight from the LLM and key lookups fall back to PostgreSQL. A cache outage makes the gateway slower, not broken.
Instead of
Treating Redis as required, which made it a single point of failure.
Cost
During a Redis outage, rate limiting is skipped. I chose availability, and documented the trade-off.

Fail over only on "their problem"

Why
Timeouts, 429s and 5xx errors might succeed elsewhere, so they go to Gemini. A 400 or 401 is my bug, and failing over would just hide it.
Result
Only retryable errors count toward the circuit breaker, so bad customer requests can never take Groq out of service for everyone.
Cost
Classifying errors by hand, and keeping that list right as providers change.

Per-tenant cache keys

Why
Real prompts contain private data. A shared cache could serve one company's answer to another.
Instead of
One global cache, which has a higher hit rate.
Cost
Fewer cache hits across tenants. Safe by default was worth it.

PostgreSQL for money, in whole micro-dollars

Why
Spend is updated with one atomic upsert that returns the new total, so concurrent requests never lose a cent. Integers are exact, and costs round up so the gateway never undercharges.
Instead of
Floating point, or keeping spend only in Redis.
Cost
A database write on every LLM call, plus a cache copy to keep in sync.

What broke, and how I fixed it

I broke every feature on purpose before trusting it. These taught me the most.

20 identical requests made 20 LLM calls

Symptom: a load test fired 20 identical questions at the same moment, and every one of them called the LLM.

Cause: all 20 checked the cache within a few milliseconds, before the first answer came back. A cache stampede.

Fix: a Redis lock so one request fetches and the rest wait. Now 1 call instead of 20, with about 50 ms extra for the waiters.

The fix almost failed on a cold start

Symptom: right after a restart, the first LLM answer took about 6 seconds, while waiters gave up after 5.

Cause: a wait timeout tuned for a warm app. One second slower, and all 19 waiters would have stampeded anyway.

Fix: a timeout based on measured LLM latency, not a guess. Lesson: test the first request, not just the average one.

A revoked API key kept working

Symptom: I revoked a key, and it still got answers.

Cause: the key lookup was cached in Redis for 5 minutes. The database changed, the copy did not. Cache drift, and here a security hole.

Fix: delete the cached copy after the database transaction commits, with the TTL as a safety net. A regression test proves a revoked key fails immediately.

A Redis outage froze every request

Symptom: I stopped Redis, and requests hung for a minute, then failed with 500 even though the LLM was fine.

Cause: a 60 second default timeout, and a cache treated as required.

Fix: 2 second timeouts, then fail open. Requests still get answers during a Redis outage, and the client reconnects on its own when Redis returns.

A wrong admin token got a 400, not a 401

Symptom: an unauthenticated request with a bad body was told what was wrong with the body.

Cause: request validation ran before the token check, leaking API details to anyone.

Fix: moved authentication into a servlet filter, so it runs before validation and before any controller.

The backup model had been retired

Symptom: during a simulated Groq outage, every request failed with 502.

Cause: the Gemini model I chose still appeared in the model list, but was no longer available to new accounts.

Fix: a one-line config change, since models live in config, not code. Lesson: test your fallback before you need it.

By the numbers

20 to 1LLM calls for 20 identical requests at once
~6 msper cached answer, versus 0.5 to 2 s from the LLM
7 of 7requests answered during a simulated Groq outage

To be honest about it: these were measured on my laptop with small samples, not under production load. The circuit breaker opened after 5 failed calls, as configured, and startup dropped from about 70 seconds to 7 after moving to a proper Docker image. Load testing at scale is part of the AWS phase.
